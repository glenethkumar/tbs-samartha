1. EXECUTIVE SUMMARY & OBJECTIVES
================================================================================
Antigravity designed, architected, implemented, tested, and documented a complete,
production-grade, full-stack decision-support platform named "FleetYield AI" for
bus fleet operators (enhancing the TBS FleetOS ecosystem).

Key Objectives Met:
- Deterministic, explainable rule-based demand classification and yield management.
- Hard bounding of all recommended fares within operator min/max guardrails.
- Data-quality shields that block recommendations on stale (>24h) or invalid data.
- Full Human-in-the-Loop (HITL) operator approval, rejection, and manual override.
- Immutable SQLite persistence for inventory, recommendations, decisions, and audit events.
- Dynamic counterfactual simulation comparing dynamic fares against a fixed baseline.
- High-fidelity UI/UX replicating the modern AVGBUS dashboard design reference.
- 100% test coverage for core business logic, validation rules, and integration flows.

3. BACKEND ARCHITECTURE & PERSISTENCE LAYER
================================================================================
Antigravity constructed a clean relational schema in SQLite across 5 relational tables:

1. `trips`
   - Stores master trip inventory:
     * `trip_id` (PRIMARY KEY)
     * `route_name`, `origin`, `destination`, `departure_time`
     * `total_seats`, `booked_seats`
     * `base_fare`, `current_fare`, `min_fare`, `max_fare`
     * `data_updated_at`, `data_source_label`, `bus_type`, `route_distance_km`, `operator_notes`
     * `created_at`, `updated_at`

2. `booking_snapshots`
   - Captures time-series booking pace across observation windows:
     * `snapshot_id` (PRIMARY KEY)
     * `trip_id` (FOREIGN KEY -> trips)
     * `recorded_at`, `booked_seats`, `available_seats`, `occupancy_percent`

3. `recommendations`
   - Persists every generated yield pricing recommendation:
     * `recommendation_id` (PRIMARY KEY)
     * `trip_id` (FOREIGN KEY -> trips)
     * `generated_at`, `current_fare_at_generation`, `base_fare_at_generation`
     * `recommended_fare`, `fare_difference`, `fare_difference_pct`
     * `min_fare`, `max_fare`, `demand_category`, `explanation`, `rule_applied`
     * `contributing_factors_json`, `booking_pace_info_json`, `validation_status`
     * `policy_version`, `source_label`, `is_clamped`, `clamped_reason`, `notice`

4. `operator_decisions`
   - Logs operator human-in-the-loop decisions:
     * `decision_id` (PRIMARY KEY)
     * `recommendation_id` (FOREIGN KEY -> recommendations)
     * `trip_id` (FOREIGN KEY -> trips)
     * `decision_type` (APPROVED | REJECTED | OVERRIDDEN)
     * `decision_fare`, `effective_fare`, `previous_fare`
     * `reason`, `actor_label`, `decided_at`

5. `audit_events`
   - Immutable audit trail for system governance:
     * `event_id` (PRIMARY KEY)
     * `trip_id`, `event_type`, `payload_json`, `actor`, `created_at`

Synthetic Seed Dataset (`backend/app/seed.py`):

4. DOMAIN SERVICES & ALGORITHMS DEVELOPED
================================================================================

1. ValidationService (`backend/app/services/validation_service.py`)
   - Functions Developed:
     * `validate_trip(trip)`: Evaluates trip data integrity against 5 strict rules:
       - Capacity check: `booked_seats <= total_seats`.
       - Non-negative validation: `booked_seats >= 0`, `total_seats > 0`.
       - Boundary consistency: `min_fare <= current_fare <= max_fare` and `min_fare <= base_fare <= max_fare`.
       - Freshness guard: checks if `(now - data_updated_at) <= 24 hours`.
       - Zero total seat defense: prevents divide-by-zero errors in occupancy calculations.
     * Returns structured `ValidationResult` containing `is_valid`, `is_stale`,
       `can_recommend`, and specific error issue strings.

2. DemandClassifier (`backend/app/services/demand_classifier.py`)
   - Functions Developed:
     * `classify(trip, snapshots)`: Deterministic scoring engine combining:
       - Occupancy Tier:
         * >70.0% -> High Demand
         * 30.0% - 70.0% -> Medium Demand
         * <30.0% -> Low Demand
       - Booking Velocity (Pace): Calculates seat booking rate per hour across snapshot history.
       - Departure Horizon Factor: Evaluates days remaining until bus departure.
     * Generates transparent, human-readable rationales and structured contributing factor metadata.

3. PricingPolicy (`backend/app/services/pricing_policy.py`)
   - Functions Developed:
     * `calculate_fare(trip, demand_tier, pace_info)`: Bounded pricing algorithm:
       - Base adjustment multipliers:
         * High Demand: +10% to +20% (default +15%)
         * Medium Demand: 0% adjustment (preserves baseline or pace micro-adjustment)
         * Low Demand: -5% to -15% (default -10% discount to stimulate volume)
       - Strict Mathematical Clamping:
         `clamped_fare = max(trip.min_fare, min(trip.max_fare, raw_fare))`
       - Commercial Rounding: Rounds fares to the nearest ₹10.
       - Discloses clamping reason whenever the raw fare hits the boundary ceiling or floor.

4. RecommendationService (`backend/app/services/recommendation_service.py`)
   - Functions Developed:
     * `generate_recommendation(trip_id)`:
       - Invokes `ValidationService`. If data is stale or invalid, recommendation generation is blocked with a structured explanation.
       - Invokes `DemandClassifier` and `PricingPolicy`.
       - Inserts record into `recommendations` table.
       - Emits audit event `RECOMMENDATION_GENERATED`.

5. OperatorService (`backend/app/services/operator_service.py`)
   - Functions Developed:
     * `record_decision(recommendation_id, decision_type, decision_fare, reason, actor_label)`:
       - Enforces strict validation on manual overrides: if `decision_fare < min_fare` or
         `decision_fare > max_fare`, the override is rejected with an HTTP 400.
       - If `APPROVED`: updates trip's `current_fare` to `recommended_fare`.
       - If `OVERRIDDEN`: updates trip's `current_fare` to operator's valid custom fare.
       - If `REJECTED`: retains previous current fare without modifications.
       - Updates `operator_decisions` and updates `trips.updated_at`.
       - Emits audit event `OPERATOR_DECISION_RECORDED`.

6. AuditService (`backend/app/services/audit_service.py`)
   - Functions Developed:
     * `log_event(trip_id, event_type, payload, actor)`: Persists structured immutable event logs.
     * `get_events(trip_id, event_type, limit)`: Provides filtered event retrieval.
     * `get_event_types()`: Returns available system event types.

7. SimulationService (`backend/app/services/simulation_service.py`)
   - Functions Developed:
     * `run_simulation(demand_multiplier, price_elasticity, trip_ids)`:
       - Mathematical counterfactual simulation:
         * Baseline Scenario: Fixed `base_fare` with standard observed bookings.
         * Dynamic Scenario: Recommended yield fares adjusted with price elasticity model:
           `% Demand Change = -Elasticity * % Price Change`
         * Capacity limit capping: simulated bookings cannot exceed total seat capacity.
       - Computes fleet-wide revenue delta, occupancy delta, and per-trip breakdown.
       - Clearly discloses synthetic assumptions to prevent false financial claims.

8. TripService (`backend/app/services/trip_service.py`)
   - Functions Developed:
     * `list_trips(q, demand, data_status, sort_by, sort_order)`: Filtering and sorting inventory.
     * `get_trip(trip_id)`: Deep-fetch trip including snapshots, latest recommendations, and decision history.
     * `create_trip(trip_data)`: Validates and persists new trip records.
     * `update_trip(trip_id, patch_data)`: Validates bounds and updates trip parameters.
     * `calculate_fleet_summary()`: Aggregates real-time KPI metrics.

9. DATA QUALITY, GUARDRAILS & HUMAN-IN-THE-LOOP SAFETY
================================================================================
- Stale Data Guard: If a trip's data has not been updated within 24 hours, the system
  flags the trip as STALE (`TRIP-STALE-901`) and blocks recommendation generation.
- Capacity Consistency Guard: If `booked_seats > total_seats` (`TRIP-INVALID-902`),
  the system flags INVALID and halts recommendation execution.
- Hard Min/Max Fare Clamp: Recommended fares can never exceed `max_fare` or fall below `min_fare`.
  Any boundary hit is explicitly recorded in `clamped_reason` (`TRIP-CLAMP-850`).
- Operator Override Validation: Operators cannot override a fare outside `[min_fare, max_fare]`.
- Decision-Support Only: The system never applies fare updates automatically without explicit
  human operator approval or override.

11. PRICING ENGINE & BASELINE SIMULATOR ENHANCEMENTS (PHASE 2)
================================================================================

1. Documented, Unified Demand Thresholds:
   - Preserved one central configuration across backend (`config.py`), UI (`Assumptions.tsx`, `Settings.tsx`), documentation, and automated tests:
     * Low Demand: < 30.0% occupancy (-10% fare adjustment)
     * Medium Demand: 30.0% - 70.0% occupancy (0% baseline retention)
     * High Demand: > 70.0% occupancy (+15% premium yield adjustment)

2. Strict Pricing Policy Input Validation:
   - Added validation in `PricingPolicy.calculate_recommendation`:
     * Rejects non-positive fares (`base_fare <= 0`, `current_fare <= 0`, `min_fare <= 0`, `max_fare <= 0`).
     * Rejects inverted boundaries (`min_fare > max_fare`).
     * Rejects base or current fares outside `[min_fare, max_fare]`.
     * Rejects invalid occupancy percentages (`occupancy < 0` or `occupancy > 100`).
     * Rejects unrecognized demand categories.
   - Enforced nearest ₹10 commercial rounding while strictly respecting `[min_fare, max_fare]` clamping bounds.

3. Complete Recommendation Isolation:
   - Recommendation generation (`/api/recommendations/generate`) only calculates and stages proposed fares.
   - External fare publication and operational adoption strictly requires explicit operator approval (`/api/decisions`), maintaining complete separation of concerns.

4. Baseline Simulator Mathematical Guarantees:
   - Identical initial trip conditions for both Fixed-Fare and Dynamic Pricing scenarios.
   - Non-negative integer simulated bookings: `max(0, round(...))` strictly bounded by `trip.available_seats`.
   - Guaranteed non-negative bookings and revenues under all market elasticities.
   - Exact recalculation of occupancy and revenue from final simulated bookings.
   - Explicit Underperformance Detection:
     * Discloses `dynamic_underperforms_baseline` flag and explanation when dynamic pricing underperforms the fixed baseline (e.g., Inelastic Market where discounting off-peak seats erodes revenue without volume gain).
   - Truthfulness disclaimer: Model labeled strictly as decision-support simulation, never asserting that simulated models prove real-world financial gain.
   - 4 Pre-configured Benchmark Scenario Presets:
     * Balanced Market (Normal Elasticity)
     * Inelastic Market (Underperformance Scenario: -1.9% dynamic revenue drop)
     * Elastic Backlash (High Price Sensitivity: -1.5% dynamic revenue drop)
     * Peak Holiday Surge (Strong Inelastic Demand: +11.1% dynamic yield lift)

5. Comprehensive Automated Test Suite (29/29 Passing):
   - Unit tests covering fare boundaries, currency rounding, overbooking prevention, zero occupancy, full buses (100%), invalid inputs, and dynamic underperformance.
   - Integration tests covering persistence, audit logs, duplicate decision prevention, stale fixture blocks, and API workflows.

12. EXPLAINABLE PRICING CONFIDENCE & EVIDENCE QUALITY FRAMEWORK (PHASE 3)
================================================================================

1. Three-Tier Deterministic Evidence Quality Model:
   - Strong Data:
     * All required inputs valid, fresh (data freshness age <= 120 minutes).
     * Departure time in the future.
     * Observation window >= 2.0 hours for reliable booking pace calculation.
     * Confidence score: 0.90 - 0.95.
   - Limited Data:
     * Recommendation computable using core occupancy and boundaries.
     * Observation window < 2.0 hours or sparse historical velocity.
     * Clearly flagged with warnings so operators exercise manual scrutiny.
     * Confidence score: 0.70.
   - Insufficient Data:
     * Triggered by stale data (> 120 minutes old), negative values, inverted bounds, or missing critical fields.
     * Generates an explicit `BLOCKED` recommendation status.
     * Blocks automated algorithmic fare shifts and preserves current fare safely.
     * Confidence score: 0.00.

2. Comprehensive 7-Point Explainability Audit Details:
   - Preserved and exposed for every trip recommendation:
     1. Current occupancy percentage and exact threshold applied (<30% Low, 30-70% Medium, >70% High).
     2. Booking pace with timestamped observation window (`window_start`, `window_end`, `window_hours`, `bookings_per_hour`).
     3. Time until departure (`hours_to_departure`, human-readable days/hours string).
     4. Last successful data-update timestamp and data age in minutes.
     5. Detected missing, stale, invalid, or inconsistent input items (with explicit blocker descriptions).
     6. Evaluated pricing rules and rationale factors applied.
     7. Recommended fare clamped strictly within trip minimum (`min_fare`) and maximum (`max_fare`) bounds.

3. End-to-End Persistence & Backend Services:
   - Added `evidence_quality_status` and `evidence_quality_details` to SQLite database tables (`trips`, `recommendations`) and Pydantic models.
   - Updated `DemandClassifier` to produce structured observation window metadata.
